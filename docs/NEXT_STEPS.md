- 检查 git status 与 git diff，逐项确认哪些实现属于项目源码。
- 纳入 Rust/Python 源码、构建/部署脚本、CI、schema、受许可的测试夹具及技术文档。
- 排除 ocgcore/worker 等构建产物、卡库与卡图、个人 engine 配置、运行快照/报告、凭据和机器绝对路径数据。
- 用审阅后的提交固定当前 M0–M4 状态；保留上游提交、数据快照和构建哈希记录。

**验收：** 干净工作树能够说明重建前提；敏感/大型本机资产未进入版本库；从提交可找到当前源代码和部署说明。

**现状：** 本轮不依赖 jsonschema 的 4 个 Python 用例通过；全量 unittest 因 jsonschema 缺失无法导入 Schema 测试。当前解释器安装依赖的临时文件写入被拒绝。

**行动：**
- 在可写的 Python 环境中安装项目声明的 test extra，确认使用的是仓库虚拟环境。
- 运行完整 Python unittest discovery，保留命令和结果。
- 增加/补完 combo-result Schema 的负例，验证必需字段、嵌套结构及错误报告；检查 Python、Rust 和 JSON Schema 对同一报告的理解一致。

**验收：** 全量 Python 测试运行完成；Schema 的成功/拒绝样例覆盖主要输入与输出；部署/测试文档记录解释器和依赖前提。

## 3. 固化本机 MVP 的可复现验收

**行动：**
- 按 DEPLOYMENT.md 从当前配置执行 doctor、smoke、Rabbit analyze 和独立 replay。
- 保存不含私有卡库内容的验收摘要：引擎/数据 ID、配置、budget、节点数、线路 ID、结束原因及重放状态。
- 用固定 node budget 比较线路 ID 和报告；将墙钟 time_budget 测量作为性能观测，不作为精确回归。
- 记录部署包装使用绝对路径的限制，确定移动机器时的配置生成方式。

**验收：** 同一输入和固定预算可复现线路标识；每条展示的候选可从报告独立重放；不完整/未知线路不能伪装成已验证。

## 4. 定义 M5 覆盖集并逐步扩卡

先由维护者选一组优先卡组和要覆盖的核心牌。对每个新增用例：
- 固定卡组、起手、引擎和数据快照。
- 记录关键提示、原始消息样例、状态变化和预期交互。
- 先验证 engine adapter 的协议解析，再接入搜索和评分。
- 对照人工基准线路，并测试未知 opcode/decision 的安全降级。

**验收：** 新卡组的线路能完整执行并独立重放；覆盖范围及未支持效果在报告中可见；旧 fixture 仍稳定通过。

## 5. 增加对手交互场景

在覆盖集已稳定后，选定手坑、先后攻和后攻解场场景；将对手动作时点/策略作为输入；比较不中断、被中断和恢复线路。每类场景单独统计引擎调用、分支数和预算截断情况。

**验收：** 场景输入可以精确复现，输出显示交互与恢复证据，并区分未知策略；不能只凭终场启发式判断“抗手坑”。

## 6. 评估随机起手，再做构筑

实现可控 seed、样本集和统计汇总，先测固定牌组，再加入字段检索和不完整卡组补全。构筑器要处理合法性、锁定/排除、用户目标和预算；候选进入排名前必须通过多起手评估。

**验收：** 汇总报告展示样本数、置信区间、失败原因、数据版本、引擎版本和预算截断；卡组可追溯生成且通过禁限表校验。

## 7. 最后拓展服务与学习型排序

CLI JSON 合同稳定后设计 HTTP/API 和网页；训练排序器需要真实且覆盖足够的轨迹标签，并用同一预算与启发式基线离线比较。

**验收：** API 可提交、查询、取消分析任务并取回可重放报告；模型仅在经过基准证明有收益后成为可选排序器，不更改规则执行来源。
