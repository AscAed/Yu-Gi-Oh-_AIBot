## 1. 结论摘要

项目已从最初的工程骨架推进到 **M0–M4 本机 MVP**：固定版本的 x64 ocgcore 和 Lua 运行资产、官方卡片目录与 OCG 禁限表快照、隔离 worker 的真实决斗生命周期、带限额的 Combo 前缀搜索与启发式评分、候选线路独立重放，以及本机 CLI/部署包都已经存在，并通过本机端到端执行。

当前产品边界必须准确理解为：**给定完整卡组和固定五张起手，在 OCG/MR5 先攻首回合、无对手干扰的场景下，搜索并排序可由当前本机引擎重放的展开线路。** 这不是自动构筑器，也没有证明搜索到全局最优卡组或线路。评分是启发式，效果覆盖有限；目前测试牌组是 Rabbit 示例。手坑、后攻解场、随机起手统计、字段构筑/补全和 HTTP/网页都还未交付。

本轮验证再次确认 Rust 格式、静态检查、工作区测试、opt-in 真实引擎测试、CLI doctor、数据状态、牌组校验、smoke、combo analyze 和独立 replay 均通过。完整 Python 测试未能在当前解释器复验：环境缺少可选依赖 jsonschema，且该解释器写临时文件持续遭到 PermissionDenied；四个不依赖该包的 Python 子套件通过。因此 Python Schema 测试应保持“未验证”，不能沿用早期对话中“6 项已通过”的记录作为当前证据。

源代码和文档尚未形成 Git 中可复现的提交：HEAD 仍是初始提交，工作分支为 codex/combo-mvp，大部分项目文件未跟踪。发布包与引擎运行资产在 dist/ 和 data/runtime/ 中并被忽略。完成当前审查后，最优先的工程动作是选择应纳入版本控制的源文件，完成审阅并建立首个可追溯基线；本审查没有暂存或提交文件。

## 4. 能力成熟度与不足

### 已交付且有真实证据

- 固定版本的 Windows x64 引擎运行路径，ABI 探针和运行资产哈希检查。
- 可追溯的本机卡库/禁限数据快照、别名解析、OCG 规则和 YDK/请求牌组校验。
- ocgcore 的真实决斗生命周期、提示响应、原始协议帧保留、失败隔离及回放。
- 以完整引擎前缀为状态的有界 Combo 搜索、缓存、终场信息、解释性启发式评分和稳定线路标识。
- CLI 的数据导入、诊断、牌组校验、搜索、重放以及本机发布脚本。

### 部分覆盖或存在局限

1. **卡效与评分覆盖有限。** rabbit-v1 对受支持卡片集合中的少数终场组件计分，不能把总分解释为胜率、抗干扰力或卡组强度。扩大卡组前要先建立效果、消息、提示和评分的逐卡回归。
2. **场景很窄。** 当前固定五张起手、先攻第一回合、无对手动作。未形成对手策略、连锁交互或“在何处吃手坑仍能继续”的验证。
3. **搜索有界。** Beam 会剪枝；time_budget 使墙钟预算下访问到的节点数变化。应报告实际预算与终止原因，使用固定 node budget 做确定性比较。
4. **数据包是本机部署资产。** 发布包配置记录 D: 盘下的绝对路径；移动机器或目录需要重建/重写配置。dist 和 data/runtime 被忽略，不能依靠 Git checkout 单独还原本次运行。
5. **Python 全量验证欠证据。** 当前解释器不能装入测试额外依赖，jsonschema 测试未运行成功；早期记录的 6 项通过不等于本轮复验。
6. **尚无产品服务。** 没有 HTTP 服务、网页、用户任务管理或持久化分析 API。

## 5. 主要风险与处理原则

- **假阳性“引擎验证”：** 所有输出应继续区分 engine_verified、partial/unsupported 和 heuristic。未识别决策停止该分支；不完整解析不得升级成已验证。
- **评分语义漂移：** 每次扩充评分都要保留组成项、覆盖范围和反例；在训练/胜率数据到来前不把启发式当胜率。
- **搜索漏解：** 将 node budget 与 time budget 区分；记录剪枝、完成结果数和终止理由，使用固定样本集做回归。
- **版本不可复现：** 引擎、Lua、cards.cdb、banlist、协议和报告都要保留版本/哈希；报告需能指回完整输入与运行配置。
- **工作区不可追溯：** 首个必要工程门槛是建立干净、可审阅的 Git 基线，同时确保不把外部引擎二进制、个人配置、数据库或忽略目录中的报告提交进去。

## 6. 分阶段改进方案

1. **M4 收尾：可复现交付。** 选择并审查需要跟踪的源文件，补全 Python 测试依赖验证，定义一条从干净 checkout 到本机部署/重放的操作路径。
2. **M5 覆盖扩展：** 从一组正式测试卡组开始，逐步补充消息解析、提示类型、卡片效果和终场指标；未知协议继续安全停止。每组以真实引擎回归、schema 负例和报告重放通过为准入条件。
3. **M6 交互情景：** 加入可配置先后攻、手坑与后攻解场牌；显式建模对手动作假设并展示中断点、可续展线路和代价。
4. **M7 统计评估：** 对固定卡组和固定随机种子集合抽取起手，统计可展开率、终场分布、线路多样性、失败原因和区间；用基线版本做回归。
5. **M8 构筑与补全：** 先做好卡片检索、字段查询、锁定/排除约束和合法候选生成，再连接真实引擎的多手牌评估。构筑目标和计算预算必须可解释。
6. **M9 产品界面/排序模型：** CLI JSON 合同稳定后再提供 HTTP/API 与网页；有足够标签后评估学习型排序，保持规则执行仍由 ocgcore 负责。

## 7. 到最终目标的差距

离完整目标还差完整卡片/效果覆盖、字段驱动与部分牌组构筑、手坑及对手行动树、随机起手统计验证、可解释构筑目标、稳定产品 API/UI，以及可从版本库重建的发布流程。现有 MVP 已打通最难的第一条真实纵向切片——固定数据与引擎版本下，从输入牌组/起手到搜索、终场报告和独立重放——后续工作应围绕扩大这条闭环的覆盖，而不是把静态假设伪装成已验证功能。
