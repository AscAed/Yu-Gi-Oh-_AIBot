## P4内部交付序列

```text
可靠异常证据与端到端安全续跑
    → 完整首回合规则模型与原生认证
    → 正式 v6 规划/报告/CLI
    → 冻结人工基准及 16+32 手评估
    → 独立干净双资产部署与最终兼容验收
```

P4内部不得跳过上一关口，也不得用分类条目数、规划器自预测、故障注入或单条成功线路代替规则认证。这些依赖不阻塞P2/P3独立工程。

## 阶段与退出条件

### R1：异常证据闭环与安全续跑

- 完成执行、查询、结束阶段、见证/审计/重放、预算、worker 和落盘失败矩阵。
- 首项R1a固定首次调用返回结果级错误及查询捕获失败的报告/验证器回归；随后R1b再将真实执行进度改为可持久化状态机。
- 让一次真实自主执行在安全检查点暂停、重开并续跑至完成；核对计划身份、实例映射、首次预测、前缀、资源、调用费用和独立重放。
- 调用中崩溃作为费用未知单独报告，不能退款或借旧局面伪造恢复锚点。

### R2：完整语义与规则认证

- 维护 86 项场景内规则逐项状态：知识来源、模型实现、正反例、独立资格及灰响应证据分开记录。
- 覆盖资源循环、召唤/素材、连锁/效果改写、持续限制和延迟处理；每项按规则特性选取可观察断言。
- 每个成功推荐依赖的状态转移均可由独立原生前缀、真实查询和重放支持；未知规则必须拒绝依赖。

### R3：正式 v6

- 对外规划、分析、执行/恢复及报告合同版本化；旧 v1–v5 请求、身份及重放行为由回归锁定。
- 响应策略只使用有实际合法响应证据的效果；预测、观测和验证后比较分别留证。
- 正式 CLI 入口要求完整语义覆盖门禁。局部诊断/验真命令保持与正式规划入口明确区分。

### R4：冻结样本评估

- 语义关口通过后，冻结 16 手功能矩阵、32 手赛事矩阵、独立人工基准、策略、随机种子和调用预算。
- 通过可恢复的顺序编排、账本续跑、Schema 校验及 Rust 独立重放；重复运行身份与收费序列一致。
- 分别报告无干扰达成、合法响应、我方应对、灰后恢复、覆盖不足、未触达、未知、预算截断和有界未找到。
- 结果只称为固定样本上的目标达成比例，不外推为胜率或全局最优。

### R5：最终部署与兼容验收

- 在独立干净 checkout 按固定版本离线构建 Rust/Python 与双资产运行包；记录源码、引擎、Lua、CDB、牌表、知识包和可执行文件身份。
- 运行格式、Clippy、Rust/Python 默认测试、显式原生测试、doctor、旧/新报告重放及负例篡改检查。
- 旧入口与新入口按 schema 分派；不删除仍被兼容或回放依赖的实现。

## 发布和范围约束

中文字段认证、主题构筑和自动建议仍未实现；工作台只支持草稿管理与未核验的本地名称检索。构筑建议依赖其实际使用的知识与评估证据。后攻、完整对局和任意对手不属于首项最优性问题，学习型排序不是必经关口。产品基础工具、v6或代表机制通过均不能标最终AI完成。

全部正式OCG及全局最优是最终要求，不能用抽样评估或budget排名替换。相关可行性、循环与停止条件见[OPTIMALITY_RESEARCH](OPTIMALITY_RESEARCH.md)。当前无可信总工期，不把文档路线当作算法已可行的保证。
