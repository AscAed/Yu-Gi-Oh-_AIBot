# 项目路线图

## 2026-10-14 当前阶段

M4.1 已建立源码基线并恢复 Python 全量验证；干净 checkout 验收结果见 TESTING.md。M5 首版已加入幻影骑士团效果语义、条件联动、目标规划及引擎验证，交付范围见 SEMANTIC_PLANNING.md。接下来先扩展同一语义闭环的真实回归，再做单次手坑中断与恢复、多起手验证、构筑诊断。下文原 M5 的扩卡工作应包含效果语义和因果规划，不仅是新增评分规则。

## 路线原则

M0–M4 已交付本机 MVP：固定 x64 引擎和数据版本、真实引擎执行、受预算限制的 Combo 搜索、启发式评分、CLI、部署和独立重放。后续版本以一条条真实、可复验的能力闭环扩展，不用静态牌效或未完成效果模拟替代引擎证据。

每一阶段需保留：输入与场景、规则/数据/引擎版本、搜索预算、结束原因、解析覆盖状态、候选线路、原始验证/重放证据和已知限制。分数和执行正确性始终是两个维度。

## 阶段与退出门槛

### M4.1 — 交付收尾与可复现基线

**目标：** 让当前 MVP 可由维护者审阅、追溯，并能解释从源码到本机部署的差异。

**工作：**
- 审查 Git 跟踪范围，纳入源代码、构建脚本、schema、fixture 与文档；排除本机引擎二进制、卡图、个人配置、外部数据库和运行报告。
- 解决 Python test extra 的安装/临时目录问题，重跑全量 Python Schema 与契约测试。
- 定义干净 checkout、本机资产准备、构建、部署、doctor、smoke、analyze、replay 的版本化步骤。
- 审查报告元数据是否足以定位输入、卡库、禁限表、引擎、配置、搜索预算和评分版本。

**退出条件：** 源码基线经维护者审阅并进入版本控制；Python 全量测试有可复验结果；部署步骤不依赖未说明的本机状态；Rabbit 固定 node budget 的报告可以重放。

### M5 — 效果语义与因果规划

**目标：** 用结构化效果知识、条件联动和目标规划扩展 Rabbit MVP，并保留每次选择的事前依据与真实引擎证据。幻影骑士团首版已经交付；继续扩大逐效果与不同起手的回归覆盖。

**工作：**
- 维护独立知识版本、来源哈希及逐效果支持范围；未知条件不视为满足。
- 在引擎执行前生成有界方案和候选比较，核对费用、资源、次数、触发与后续限制。
- 按原始提示绑定效果与卡片实例，记录预测差异；成功推荐必须独立重放。
- 先选定代表性卡组和覆盖卡片，再记录这些卡在引擎中的消息、提示、效果、终场指标和路径。
- 为新增 opcode 建立原始字节样例和类型化解析回归；新增决策类型需明确可响应/不可响应范围。
- 扩充评价规则，并为每个评分项写明依据和不覆盖的属性。
- 比较真实引擎线路与基准手工路线；未知信息继续标记 partial，未知决策停止分支。

**退出条件：** 每个纳入的卡组 fixture 都能从固定请求运行、得到可解释报告并独立重放；负例验证未知消息不会被误标为完整/已验证；报告声明评分覆盖范围。

### M6 — 对手交互与场景推演

**目标：** 推演指定手坑、阻断点和后攻解场，明确对手假设。

**工作：**
- 将先后攻、对手手牌/场上牌、可用次数和响应策略纳入显式场景输入。
- 支持用户指定的关键手坑/解场牌，记录交互发生时点、被中断状态和恢复线路。
- 输出场景假设与未覆盖响应；不把单一对手策略概括成通用抗性。
- 从单交互开始，逐步增加连锁和多响应分支，控制分支预算。

**退出条件：** 每个场景可由固定输入和版本复现；输出有完整引擎证据，正确区分被打断、可继续、未知交互；预算结束时保留已完成结果和终止原因。

### M7 — 随机起手统计与评估

**目标：** 从固定起手分析走向可量化的牌组级比较。

**工作：**
- 设计可复现的抽样种子、样本量和置信区间；将其作为评估配置，而非隐藏默认值。
- 汇总展开成功率、终场分布、可用交互、死手/失败原因、线路多样性及资源成本。
- 建立基准请求与版本间差异报告；将引擎覆盖不足单列出来。
- 分析有限预算对结果的影响，并区分采样误差与搜索剪枝误差。

**退出条件：** 相同数据/引擎/seed 配置可复现样本序列与汇总；报告包含样本数、区间、失败率、预算截断率和版本；指标经过领域审阅。

### M8 — 字段构筑与不完整卡组补全

**目标：** 支持从主题/字段或用户已有卡组生成合法的候选构筑。

**工作：**
- 提供以固定快照为依据的字段/卡片检索、候选池和卡片来源。
- 支持用户锁定、排除、固定张数、预算/规则限制等约束，并报告不可满足条件。
- 先生成合法候选，再连接 M7 多起手评估与 M5/M6 引擎验证。
- 在目标函数中明确展开稳定性、终场资源/交互和构筑约束的取舍。

**退出条件：** 每个输出卡组均通过规则与禁限校验；保留输入约束、数据快照和生成过程；多个候选可解释、可比较、可重跑。

### M9 — 服务与用户体验

**目标：** 在 CLI JSON 合同稳定后提供可集成的 API 或网页体验。

**工作：**
- 基于现有 request/report schema 设计 HTTP 生命周期、进度、取消、超时和错误类型。
- 提供报告版本兼容策略、任务状态持久化与部署/资产诊断。
- 仅在有足量已验证轨迹和正确标签时评估学习型排序；保留启发式基线与离线对比。
- LLM 可用于自然语言意图提取和结果说明，不作为规则执行权威。

**退出条件：** 服务边界不绕过领域校验、搜索预算、引擎验证标签和数据来源；用户可导出能重放的分析请求/报告；排序模型通过同预算离线基准后才进入默认路径。

## 当前优先顺序

M4.1 源码基线及 Python Schema 验证已经完成，M5 已有固定起手目标闭环。下一步扩大逐效果真实回归，再推进单次指定手坑与恢复、多起手评估和构筑诊断，稳定合同后建设服务与网页。当前运行证据见 [TESTING.md](TESTING.md)，部署与资产准备见 [DEPLOYMENT.md](DEPLOYMENT.md)，总体缺口见 [PROJECT_ASSESSMENT.md](PROJECT_ASSESSMENT.md)。
